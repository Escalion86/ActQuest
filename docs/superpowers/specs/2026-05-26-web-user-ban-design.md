# Спецификация: жёсткий бан пользователя в web/cabinet

## Контекст

В текущей web/cabinet-ветке роль `ban` уже хранится в `Users.role`, но не
обеспечивает полный серверный запрет на командные действия. Забаненный
пользователь может оставаться участником команд, создавать команды и
присоединяться к ним через web API.

Цель изменений: сделать `ban` жёстким именно в web-ветке, без опоры на legacy
Telegram-код.

## Цели

- При переводе пользователя в `ban` исключать его из всех команд.
- Если пользователь был капитаном команды:
  - передавать капитанство другому участнику, если команда не пустая;
  - удалять команду, если других участников нет.
- Перед выполнением бана показывать администратору явное подтверждение с
  последствиями.
- После бана пользователь не должен иметь возможности:
  - создавать команды;
  - присоединяться к командам;
  - быть добавленным в команду через web API.

## Не-цели

- Не менять legacy Telegram-логику.
- Не вводить отдельную сущность бана или историю банов.
- Не менять существующую модель ролей за пределами `Users.role`.

## Подход

Выбран двухшаговый web API:

1. preview-эндпоинт для расчёта последствий;
2. confirm-эндпоинт для фактического бана.

Причина выбора: бан имеет нетривиальные побочные эффекты по командам и должен
выполняться осознанно, с серверным расчётом последствий до подтверждения.

## Изменения API

### 1. Preview бана

Новый route handler:

- `POST /api/cabinet/admin/users/[id]/ban-preview`

Назначение:

- проверить права администратора;
- загрузить пользователя и его членства в командах;
- определить последствия бана без записи в БД;
- вернуть структуру для confirm-модалки.

Ответ должен содержать:

- пользователя;
- общее число команд, из которых он будет исключён;
- список команд, где он обычный участник;
- список команд, где он капитан;
- для каждой капитанской команды:
  - будет ли передано капитанство;
  - кому будет передано капитанство;
  - будет ли удалена команда.

### 2. Подтверждённый бан

Новый route handler:

- `POST /api/cabinet/admin/users/[id]/ban`

Назначение:

- повторно проверить права;
- повторно вычислить последствия на сервере;
- выполнить все изменения в БД;
- перевести пользователя в `role = 'ban'`;
- вернуть итог операции и краткую сводку.

Требование по контракту:

- эндпоинт не должен доверять клиентскому preview;
- клиент не передаёт готовый список последствий как источник истины;
- сервер сам повторно пересчитывает актуальное состояние перед записью.

## Серверная бизнес-логика

Рекомендуется вынести логику в отдельный серверный модуль, например:

- `server/banUserFromWeb.js`

Модуль должен иметь два режима:

- `preview`;
- `apply`.

### Алгоритм preview/apply

1. Загрузить пользователя.
2. Найти все `TeamsUsers` записи пользователя по `userId`.
3. Собрать все связанные команды.
4. Для каждой команды определить:
   - является ли пользователь капитаном;
   - есть ли другие участники;
   - кто является кандидатом на нового капитана;
   - подлежит ли команда удалению.

### Правила по командам

Если пользователь не капитан:

- при apply удалить его membership.

Если пользователь капитан и есть другие участники:

- выбрать одного другого участника как нового капитана;
- обновить его роль до `captain`;
- удалить membership забаненного пользователя.

Если пользователь капитан и других участников нет:

- удалить команду;
- удалить связанные membership этой команды.

### Выбор нового капитана

Чтобы поведение было детерминированным и повторяемым:

- приоритет у самого раннего по `createdAt` membership среди других участников;
- если `createdAt` отсутствует, fallback по `_id` в порядке возрастания.

Это правило должно использоваться и в preview, и в apply.

## Ограничения после бана

Нужны явные server-side guards для `role === 'ban'`.

### Обязательно закрыть

- создание команды:
  - `app/api/cabinet/teams/route.js`
- самостоятельное вступление в команду:
  - `app/api/cabinet/teams/members/route.js`
- добавление пользователя в команду администратором:
  - `app/api/cabinet/teams/members/route.js`

Правило:

- если актор забанен, он не может создавать команду и вступать в неё;
- если target-пользователь забанен, его нельзя добавить в команду даже
  администратором.

### Поведение ответа

Для единообразия использовать `403` и понятные сообщения:

- `Заблокированный пользователь не может создавать команды`
- `Заблокированный пользователь не может вступать в команды`
- `Заблокированного пользователя нельзя добавить в команду`

## UI-поток в админке

Затрагиваем:

- `components/cabinet/modals/UserEditModal.js`

### Новый сценарий сохранения

Если роль изменяется на `ban`:

1. обычный `PUT /admin/users/[id]` не отправляется сразу;
2. сначала вызывается `ban-preview`;
3. открывается confirm-модалка;
4. администратор видит:
   - что пользователь будет удалён из всех команд;
   - список команд, где он капитан;
   - где капитанство будет передано;
   - какие команды будут удалены;
5. после подтверждения вызывается `ban`;
6. после успеха UI обновляет карточку пользователя и закрывает модалку.

Если роль не `ban`:

- текущий поток обычного сохранения через `PUT` сохраняется.

## Ошибки и конкурентность

### Основной принцип

Preview информирует, но не гарантирует неизменность состояния до confirm.

### Поэтому confirm должен:

- заново считать состояние;
- выполнять действие по актуальным данным;
- возвращать финальный результат даже если состав команды изменился после
  preview.

Если пользователь уже забанен:

- confirm должен быть идемпотентным и возвращать успешный результат без
  повторного каскада, либо явно сообщать, что пользователь уже заблокирован.

Предпочтительный вариант:

- вернуть `200` с признаком, что пользователь уже был заблокирован.

## Инварианты данных

После успешного бана должны выполняться условия:

- `Users.role === 'ban'`;
- у пользователя нет записей в `TeamsUsers`;
- не существует команды без участников;
- в каждой оставшейся команде не более одного капитана;
- если команда сохранена, у неё есть капитан.

## Тестирование

Так как в проекте нет полноценной тестовой инфраструктуры, минимальный объём
проверок должен включать серверные regression-тесты или verify-скрипты на
новую логику бана.

Обязательные сценарии:

1. Блокировка пользователя без команд.
2. Блокировка обычного участника нескольких команд.
3. Блокировка капитана команды с другими участниками.
4. Блокировка капитана команды без других участников.
5. Попытка забаненного пользователя создать команду.
6. Попытка забаненного пользователя вступить в команду.
7. Попытка администратора добавить забаненного пользователя в команду.
8. Повторный confirm для уже забаненного пользователя.

## Порядок реализации

1. Вынести серверную логику preview/apply в отдельный модуль.
2. Добавить `ban-preview` API.
3. Добавить `ban` API.
4. Добавить server-side guards на командные маршруты.
5. Обновить `UserEditModal` под preview + confirm.
6. Добавить проверки/тесты.

## Риски

- Расхождение preview и confirm при изменении состава команды между запросами.
- Нарушение инварианта капитана при неаккуратной последовательности обновлений.
- Частичное обновление данных при ошибке посередине каскада.

## Требование к реализации

По возможности каскад бана должен выполняться в одной согласованной серверной
операции с аккуратным порядком изменений. Если полноценная транзакция MongoDB
в текущем окружении недоступна, код должен быть написан так, чтобы минимизировать
риск зависания команды без капитана или с уже удалённым пользователем.
