# Дизайн: история изменений игры и откат состояния

## Контекст

Сейчас в проекте нет полноценной истории изменений игры как управляемой сущности.

Что есть в коде сейчас:

- `helpers/logSiteEvent.js` и коллекция `SiteEvents` фиксируют только отдельные события сайта и не хранят `before/after`;
- `Games.result` хранит snapshot результата и состава команд на момент остановки игры, но это история игрового результата, а не журнал админских изменений;
- `GamesTeams.storyProgress.history` относится только к прохождению story-квеста командой;
- основные изменения игры и связанных данных пишутся напрямую в `Games` и `GamesTeams` через API без отдельного audit trail.

Из-за этого сейчас нельзя:

- посмотреть хронологию действий над конкретной игрой;
- понять, какие именно поля были изменены;
- безопасно восстановить состояние игры на выбранную точку времени;
- предупредить оператора о последствиях rollback до выполнения действия.

## Цель

Сделать полноценную историю изменений, связанных с игрой, с возможностью:

- просматривать хронологию действий над игрой;
- раскрывать конкретную запись и видеть, что изменилось: `было` и `стало`;
- откатывать игру к выбранной записи истории;
- при откате восстанавливать состояние игры целиком на выбранную точку, включая все более новые изменения;
- показывать предупреждения о последствиях rollback, особенно для запущенной игры и для данных, влияющих на результат.

## Обязательный охват v1

В первую версию должны входить такие события:

- изменение игры;
- регистрация команды на игру;
- отмена регистрации команды;
- добавление, удаление и изменение ручных корректирующих бонусов/штрафов;
- изменение статуса игры;
- расчёт результатов и обновление результатов.

Под “изменением игры” здесь понимаются правки документа `Games`, включая поля игры, задания, бонусные и штрафные коды, модераторов, агентов, тарифы, финансы, story-настройки и другие редактируемые данные игры.

## Не делаем в v1

- не пересчитываем автоматически `updateParticipantsRatings`;
- не пересчитываем автоматически `updateParticipantsClosedStats`;
- не пытаемся откатывать внешние побочные эффекты вне БД игры, например файлы в облаке;
- не строим универсальный audit trail для всего проекта;
- не переводим проект на event sourcing.

Если rollback затрагивает данные, способные повлиять на рейтинги или закрытую статистику, система должна показать предупреждение, но не должна блокировать действие.

## Ключевое поведение rollback

Rollback работает не как “отмена одного действия”, а как восстановление состояния игры на выбранную точку истории.

Если пользователь выбирает, например, пятую запись с конца, система:

- находит состояние игры, связанное с этой записью;
- восстанавливает игру и связанные `GamesTeams` до состояния на тот момент;
- тем самым отменяет все более новые действия после выбранной записи;
- создаёт новую запись истории `rollback_applied`, которая сама фиксирует факт отката.

Rollback разрешён всегда, включая статусы:

- `active`;
- `started`;
- `finished`;
- `closed`;
- `canceled`.

Для игры в статусе `started` UI должен показывать красное предупреждение о последствиях, но действие не блокируется.

## Выбранный подход

Выбран подход `audit log + rollback snapshots`.

Он состоит из двух частей:

1. Для каждого значимого действия сохраняется запись истории с:
   - типом действия;
   - актором;
   - кратким описанием;
   - diff;
   - значениями `before` и `after`.
2. Для rollback-safe операций дополнительно сохраняется согласованный snapshot состояния игры и всех связанных `GamesTeams`, чтобы можно было восстановить систему без вычисления обратных операций вручную.

### Почему выбран именно этот вариант

- хорошо ложится на текущую архитектуру с `Games` и `GamesTeams`;
- позволяет сделать понятный UI истории;
- позволяет безопасно восстанавливать состояние по точке времени;
- не требует переписывать существующую бизнес-логику под event sourcing;
- проще поддерживать при будущих изменениях игровых API.

## Единица истории

История строится не вокруг одиночного документа `Games`, а вокруг согласованного состояния конкретной игры.

В согласованное состояние входят:

- документ `Games` по `gameId`;
- все документы `GamesTeams`, где `gameId` совпадает с игрой;
- `result` внутри `Games`, если он затронут действием.

Это важно, потому что регистрация команды, ручные корректировки времени, `outOfCompetition`, результаты и статус игры меняют не только `Games`, но и связанные записи `GamesTeams`.

## Модель данных

Нужна отдельная коллекция `GameHistoryEntries`.

### Структура записи истории

Запись должна содержать как минимум:

- `gameId`;
- `location`;
- `actionType`;
- `entityScope`;
- `summary`;
- `actor`;
- `warnings`;
- `before`;
- `after`;
- `diff`;
- `snapshot`;
- `rollback`;
- `createdAt`.

### Предлагаемая семантика полей

- `gameId`: строковый id игры.
- `location`: нормализованный город игры на момент записи.
- `actionType`: тип действия.
- `entityScope`: что именно затронуто, например `game`, `game_teams`, `result`, `mixed`.
- `summary`: короткое человекочитаемое описание карточки действия.
- `actor`: данные об инициаторе действия.
- `warnings`: список предупреждений, относящихся к записи или rollback.
- `before`: нормализованное состояние изменённого фрагмента до действия.
- `after`: нормализованное состояние изменённого фрагмента после действия.
- `diff`: компактная структура изменений для UI.
- `snapshot`: полный rollback snapshot игры и всех `GamesTeams`, если запись поддерживает rollback.
- `rollback`: метаданные отката, если запись сама создана rollback-операцией.
- `createdAt`: время записи.

### Актор

В `actor` достаточно сохранить:

- `userId`;
- `telegramId`;
- `role`;
- `name` или best-effort display name, если доступно.

Если актор не определён, запись всё равно сохраняется с пустым актором, но это не должно происходить для штатных кабинетных действий.

## Типы событий v1

Для первой версии вводятся такие `actionType`:

- `game_updated`;
- `game_status_changed`;
- `team_registered`;
- `team_unregistered`;
- `team_adjustments_updated`;
- `team_out_of_competition_changed`;
- `results_rebuilt`;
- `rollback_applied`.

Дополнительно в `game_updated` могут попадать:

- изменения заданий;
- изменения бонусных и штрафных кодов;
- изменения тарифов;
- изменения финансов;
- изменения story-конфигурации;
- изменения модераторов и агентов.

## Где писать историю

Основные точки записи истории в текущем коде:

- `app/api/[location]/games/[id]/route.js`
  - изменение игры;
  - изменение статуса игры;
  - создание snapshot результата при переходе в `finished`;
  - reset игры при возврате в `active`.
- `app/api/cabinet/games/[gameId]/teams/route.js`
  - регистрация и снятие команд;
  - изменение ручных корректировок;
  - изменение `outOfCompetition`.
- `app/api/cabinet/games/[gameId]/result/route.js`
  - пересборка `result.teamsPlaces` и `result.computed`.
- `app/api/cabinet/admin/story-editor/route.js`
  - изменения story-редактора.
- `app/api/cabinet/admin/game-status/action/route.js`
  - действия в live-контроле игры, если они меняют состояние прохождения команды и должны отражаться в истории игры.

## Серверный слой истории

Нужен отдельный серверный helper, условно:

- `server/gameHistory/recordGameHistoryEntry.js`

Его ответственность:

- получить `beforeState` и `afterState`;
- нормализовать их;
- построить `summary`;
- построить `diff`;
- определить warnings;
- при необходимости вложить rollback snapshot;
- сохранить запись в `GameHistoryEntries`.

Также нужен helper, условно:

- `server/gameHistory/loadGameRollbackState.js`

И helper отката, условно:

- `server/gameHistory/rollbackGameToHistoryEntry.js`

### Нормализация состояния

Чтобы избежать шума в diff, нужно нормализовать:

- служебные mongoose-поля;
- порядок массивов там, где он логически незначим;
- значения `undefined` / `null`;
- даты в сериализуемый формат;
- поля, зависящие от `ObjectId`, к строковому виду.

Snapshot должен сохраняться в plain JSON-форме, пригодной для прямого восстановления.

## Diff и представление изменений

UI должен показывать не сырой JSON всей игры, а понятные изменения.

Поэтому `diff` должен хранить список записей вида:

- `path`;
- `label`;
- `kind`;
- `beforeValue`;
- `afterValue`.

Примеры:

- `name` — изменено название игры;
- `status` — изменён статус;
- `tasks[2].bonusCodes[1].bonus` — изменён размер бонуса;
- `prices` — изменён список тарифов;
- `finances` — изменены финансовые записи;
- `gameTeams` — добавлена или удалена команда;
- `result.computed` — обновлён расчёт результата.

Для сложных изменений списков допустимо хранить diff блоками, а в `before`/`after` показывать нормализованные структуры целиком.

## Snapshot для rollback

Не каждая запись обязана хранить полный snapshot, но для всех rollback-safe записей в v1 snapshot должен быть обязательным.

Snapshot должен включать:

- `game`: полный сериализованный документ игры;
- `gameTeams`: полный список сериализованных `GamesTeams` для игры;
- `capturedAt`: время фиксации;
- `schemaVersion`: версия структуры snapshot для миграций в будущем.

Это даёт возможность:

- восстановить документ `Games`;
- синхронизировать состав `GamesTeams`;
- вернуть `result` в нужное состояние;
- корректно откатывать регистрацию команд и ручные корректировки.

## Алгоритм rollback

Rollback по выбранной записи выполняется так:

1. Загружается запись истории по `entryId`.
2. Проверяется, что запись принадлежит нужной игре и содержит snapshot.
3. Загружается текущая игра и текущие `GamesTeams`.
4. Текущее состояние игры также сериализуется, чтобы rollback сам можно было увидеть в истории.
5. `Games` восстанавливается из snapshot.
6. Связанные `GamesTeams` приводятся в точное соответствие snapshot:
   - отсутствующие создаются;
   - существующие обновляются;
   - лишние для этой игры удаляются.
7. Рейтинги и закрытая статистика автоматически не пересчитываются.
8. Создаётся новая запись истории `rollback_applied`.

### Важная семантика

Rollback не должен переписывать историю задним числом и не должен удалять старые записи истории.

История после rollback должна выглядеть так:

- старые записи остаются;
- появляется новая запись `rollback_applied`;
- в ней видно, к какой записи выполнен возврат и сколько более новых изменений фактически было отменено.

## Warnings

Система предупреждений нужна на двух уровнях:

### 1. Warnings в карточках истории

Если действие влияет на:

- `result`;
- состав команд;
- статус игры;
- ручные корректировки времени;

то карточка должна хранить предупреждения, которые пригодятся при rollback.

### 2. Warnings перед rollback

Перед подтверждением rollback UI должен показать предупреждения.

Обязательные случаи:

- если игра `started`, показать красное предупреждение о том, что откат затронет текущий живой прогресс;
- если rollback затрагивает `result`, состав команд или статус, показать предупреждение о возможном расхождении рейтингов и закрытой статистики, так как они не пересчитываются автоматически.

## Права доступа

История и откат доступны только:

- `admin`;
- `dev`;
- организатору игры;
- модератору игры.

Права должны проверяться не только в UI, но и на сервере.

UI-скрытие кнопки не является достаточной защитой.

Проверка доступа должна использовать ту же логику, что и уже существующие кабинетные маршруты управления игрой.

## UI

### Вход в историю

С карточки игры в кабинете добавляется новое действие `История`.

Требования:

- action-кнопка на карточке игры;
- видна только пользователям с правом управления этой игрой;
- открывает модальное окно истории.

### Модальное окно истории

Нужна новая модалка, условно:

- `components/modals/GameHistoryModal.js`

Содержимое:

- заголовок `История игры — <название>`;
- warning banner, если игра `started`;
- список карточек действий по убыванию времени;
- lazy раскрытие деталей конкретной записи;
- confirm-поток для rollback.

### Карточка действия

Каждая карточка должна показывать:

- тип действия;
- краткий summary;
- кто выполнил действие;
- когда выполнено;
- наличие warnings;
- наличие возможности rollback.

В раскрытом виде:

- секция `Что изменилось`;
- секция `Было`;
- секция `Стало`;
- секция `Предупреждения`;
- кнопка `Откатить к этому состоянию`, если запись rollback-safe.

### Confirm rollback

Перед rollback нужен отдельный confirm-диалог.

Он должен явно сообщать:

- что игра будет восстановлена на выбранную точку времени;
- что все более новые изменения будут отменены;
- что рейтинги и закрытая статистика не будут пересчитаны автоматически;
- если игра `started`, показать красное предупреждение.

## API

Для v1 нужны новые кабинетные endpoints истории игры, например:

- `GET /api/cabinet/games/[gameId]/history`
  - список записей истории;
- `GET /api/cabinet/games/[gameId]/history/[entryId]`
  - детальная запись;
- `POST /api/cabinet/games/[gameId]/history/[entryId]/rollback`
  - rollback к выбранной записи.

### Что возвращает список

Список должен содержать компактные данные карточек:

- `id`;
- `actionType`;
- `summary`;
- `actor`;
- `createdAt`;
- `warnings`;
- `canRollback`.

### Что возвращает детальная запись

Детальная запись должна содержать:

- карточечные поля;
- `before`;
- `after`;
- `diff`;
- `rollback` metadata;
- вычисленные предупреждения для confirm rollback.

## Восстановление данных при rollback

Так как rollback работает по snapshot, восстановление должно быть точным, а не частичным merge.

Это означает:

- документ `Games` заменяется согласованным набором полей из snapshot;
- `GamesTeams` для этой игры синхронизируются до exact match;
- `result` возвращается к состоянию из snapshot;
- новые поля игры, которые не существовали в старом snapshot, должны обрабатываться осторожно через `schemaVersion`.

Если в будущем структура snapshot изменится, логика rollback должна уметь отказывать в rollback старой записи понятной ошибкой, а не молча восстанавливать несовместимое состояние.

## Ошибки и граничные случаи

- если запись истории не найдена, вернуть `404`;
- если запись не принадлежит игре, вернуть `404` или `403` без утечки деталей;
- если у записи нет snapshot, rollback запрещён;
- если у пользователя нет прав, вернуть `403`;
- если snapshot повреждён или несовместим по версии, вернуть понятную ошибку;
- если rollback выполнен успешно, но он влияет на рейтинги/статистику, вернуть warnings в payload ответа;
- если текущая игра удалена, но есть история, rollback должен быть либо запрещён, либо явно поддержан как восстановление игры из snapshot; для v1 безопаснее rollback удалённой игры не поддерживать.

## Тестирование и проверка

Полноценных тестов в проекте сейчас нет, поэтому v1 должна как минимум включать:

- серверные smoke-сценарии для записи истории;
- серверные smoke-сценарии для rollback;
- ручную проверку UI-модалки истории;
- проверку прав доступа.

Минимальные сценарии:

- изменение поля игры создаёт запись истории;
- изменение статуса игры создаёт отдельную запись;
- регистрация команды создаёт запись;
- снятие команды создаёт запись;
- изменение ручных корректировок создаёт запись;
- пересборка результатов создаёт запись;
- rollback создаёт новую запись `rollback_applied`;
- после rollback игра и `GamesTeams` соответствуют snapshot выбранной записи;
- для `started` игры confirm rollback показывает красный warning;
- для действий, влияющих на результат, показывается warning о рейтингах.

## Риски

- `GamesPageClient` уже крупный, поэтому важно не раздувать его логикой diff и rollback;
- snapshot истории может занять заметный объём, особенно для игр с большим количеством заданий и команд;
- при неточной нормализации diff будет слишком шумным и бесполезным;
- rollback по живой игре `started` операционно опасен, поэтому warning критически важен;
- история может затронуть несколько разных API-маршрутов, и легко забыть встроить запись в один из них;
- story-редактор меняет крупные вложенные структуры, и там особенно важен адекватный diff без чрезмерного шума.

## Рекомендация по реализации

Двигаться поэтапно:

1. Добавить схему `GameHistoryEntries` и серверные helpers нормализации/diff/snapshot.
2. Встроить запись истории в ключевые mutation-path’ы.
3. Добавить API чтения истории и rollback.
4. Добавить UI-модалку истории и кнопку на карточке игры.
5. Добавить warnings и confirm rollback.
6. Прогнать smoke-проверки и ручные сценарии.

## Ожидаемый результат

После реализации оператор с правами управления игрой сможет:

- открыть историю игры прямо с карточки;
- увидеть последовательность действий над игрой;
- раскрыть любую запись и посмотреть, что изменилось;
- откатить игру к выбранной точке времени;
- получить предупреждение, если rollback опасен или может разойтись с рейтингами.
