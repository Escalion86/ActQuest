# Game Assignment Flags Design

**Goal:** убрать `agent` и `moder` из системных ролей пользователя и заменить их двумя явными флагами назначения в игры: `canBeGameAgent` и `canBeGameModerator`.

## Контекст

Сейчас проект смешивает два разных понятия:

- системная роль пользователя (`client`, `moder`, `admin`, `dev`, `ban`);
- возможность выбрать пользователя в игре как модератора или агента.

Из-за этого редактор пользователей хранит `moder` и `agent` как глобальные права, а доступ к игровым API частично проверяется по системной роли, хотя фактический доступ должен определяться назначением в конкретной игре.

## Целевое поведение

### Пользователь

В `Users` остаются только системные роли:

- `client`
- `admin`
- `dev`
- `ban`

В документ пользователя добавляются поля:

- `canBeGameModerator: boolean`
- `canBeGameAgent: boolean`

Они не дают никаких системных прав. Они лишь разрешают выбирать пользователя в редакторе игры.

### Редактор пользователей

В редакторе пользователя:

- убрать системные роли `Модератор` и `Агент`;
- добавить чекбоксы:
  - `Можно назначить модератором`
  - `Можно назначить агентом`

### Редактор игры

Списки выбора строятся так:

- модераторы игры: только пользователи с `canBeGameModerator === true`;
- агенты игры: только пользователи с `canBeGameAgent === true`.

### Доступ к играм

Серверные проверки доступа не должны зависеть от системных ролей `moder` и `agent`, потому что этих ролей больше не будет.

Новые правила:

- `admin` и `dev` сохраняют полный доступ;
- доступ модератора к конкретной игре определяется только присутствием пользователя в `game.moderators`;
- доступ агента к игре определяется только присутствием пользователя в `game.agents`;
- доступ агента к заданиям и story-нодам определяется существующими `agentUserIds`.

## Области изменений

### Модель и нормализация пользователя

Нужно обновить:

- схему `Users`;
- список допустимых системных ролей;
- нормализацию пользователя в кабинетных API.

### API пользователей

Нужно научить admin users API:

- возвращать новые флаги;
- сохранять новые флаги;
- фильтровать список по assignment-флагам для редактора игры.

### Игровые доступы

Нужно перевести на helper-логику:

- `app/api/cabinet/admin/game-status/route.js`
- `app/api/cabinet/admin/game-status/action/route.js`
- `app/api/cabinet/admin/photo-review/route.js`
- `app/api/cabinet/admin/task-preview/route.js`
- `app/api/cabinet/agent/games/route.js`
- `app/api/cabinet/agent/game-status/route.js`
- `server/agentGameStatus.js`
- `helpers/cabinetGameVisibility.js`

### Страницы кабинета

Страницы с жёсткой проверкой по `moder` / `agent` нужно ослабить до:

- авторизованный пользователь;
- реальные права проверяются API-слоем по игре.

Это нужно, чтобы пользователь, назначенный в игру, не терял доступ после миграции.

### Миграция данных

Нужен отдельный production-скрипт.

Скрипт должен:

- находить пользователей с `role: 'moder'`;
- выставлять `canBeGameModerator: true`;
- находить пользователей с `role: 'agent'`;
- выставлять `canBeGameAgent: true`;
- переводить системную роль в `client`;
- поддерживать dry-run и apply-режим;
- печатать итоговую статистику.

## Инварианты

- Пользователь только с флагом `canBeGameModerator` не получает доступ ни к одной игре автоматически.
- Пользователь только с флагом `canBeGameAgent` не получает доступ ни к одной игре автоматически.
- Пользователь, уже назначенный в `game.moderators`, сохраняет доступ к модераторским API этой игры после миграции.
- Пользователь, уже назначенный в `game.agents`, сохраняет доступ к агентскому кабинету и данным этой игры после миграции.
- Старые значения `role: 'moder' | 'agent'` больше не должны сохраняться через admin users API.
